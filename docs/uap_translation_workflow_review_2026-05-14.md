## 2. OCR不可記事ルール（draft_rules_v2 抜粋・運用メモ）

### 基本原則
ファイル名から読み取れる情報のみを事実として記述する。それ以外はすべて推定扱いとする。

### 確定ルール

**Rule 1: ファイル名由来情報のみ事実化**
- ファイル名に含まれる番号・日付・機関名のみを本文で断定可
- 例: `fbi-photo-b13.pdf` → 「FBI提出」「ファイル名 fbi-photo-b13.pdf」は断定可
- 例: タイムスタンプ（画像内に視覚確認できる場合）→ 断定可
- PDFのテキスト層がゼロの場合、内容記述はすべて画像の視覚観察に限定

**Rule 2: 外部背景・歴史情報の本文断定禁止**
- 資料内テキストで確認できない機関背景・事件背景を断定しない
- 例: 「この事案は〇〇年の〇〇事件に関連する」→ 禁止（本文確認不可）

**Rule 3: RecordGroup・機関番号・シリーズ構成の断定禁止**
- 「全24フレーム」「時系列順で〇番目」などシリーズ全体構成の断定禁止
- 理由: source_registry 未登録フレームへの依存が生まれるため
- 代替: 「本フレーム（bXX: HH:MM:SS）はファイル名の番号と撮影時系列順序が一致していないフレームです」

**Rule 4: 推定時の付記形式**
- 推定値には必ず `（ファイル名より推定）` または `（本文確認不可）` を付記
- 例: 「広角フレーム（スケール±15、ファイル名よりb1〜b12・b19〜b21と推定）」

## 3. 画像記事ルール（EO/IR断定禁止）

### 禁止表現と代替表現

| 禁止表現 | 代替表現 | 理由 |
|---|---|---|
| 軍用赤外線カメラ映像 | IR映像とみられる画像フレーム | 「軍用」は資料内未確認 |
| 追跡対象物 | 暗点 / 何らかの対象 | 機能断定 |
| EO/IRカメラが捕捉した | 画像中に確認できる | 意図断定 |
| 移動が確認できます | 別位置に確認できます | フレーム比較で「移動」断定は不可 |
| 追跡が継続されています | 継続して確認されています | 追跡=カメラ操作者の意図断定 |
| 丸みのある形状をしており | 丸みを帯びたにじみとして確認でき | IR解像度特性の留保が必要 |
| ズームシリーズ | ズームイン状態フレーム群 | シリーズ全体構成断定 |
| シリーズの起点 / 最終フレーム | （削除、または「確認済み範囲での最後」） | 未登録フレームへの依存 |

### 視覚観察と解釈の分離原則

本文では以下を分離して記述する。

- **視覚観察（断定可）:** 画像に見えるもの（暗点の位置・形状・数・スケール値・タイムスタンプ）
- **フレーム間比較（条件付き可）:** 「前フレーム（bXX）と比較して〇〇の位置に確認できます」
- **対象物解釈（禁止）:** 「追跡対象物」「飛行物体」「機体」「ロック」「捕捉」等

### 注意点セクションの定型文

```
ズーム状態で確認できる2つの暗点は、何らかの対象を映している可能性がありますが、
センサーアーティファクトの可能性も排除できません。
本記事は視覚的観察の記述であり、対象の性質については判断しません。
```

## 4. note投稿問題と対応

### 確認された問題

**コピペ崩れ**
- note のエディタにMarkdownを直接貼り付けると書式が崩れる
- 特に見出し（##）・箇条書き（-）・水平線（---）が不安定
- 対応: MT/TXT インポート形式を優先使用

**表崩れ**
- Markdown table（`|---|`形式）は note では正しく描画されない
- 対応: **note投稿フォーマット禁止事項**（feedback_note_formatting.md）に記録
  - Markdown table 禁止
  - 引用ブロック（`>`）禁止
  - ネスト箇条書き禁止
  - コードブロック（``` ```）禁止
  - 代替: 【原文抜粋】【要訳】＋箇条書き形式

**引用崩れ**
- `>` 引用ブロックは note で描画が不安定
- 対応: 【原文抜粋】ラベル＋通常テキストで代替

### txt/mt import 検証結果

- **MT インポート形式:** TITLE / STATUS / ALLOW COMMENTS / CONVERT BREAKS / DATE / BODY フィールド
- **拡張子:** `.txt`（note インポート仕様に準拠）
- **改行処理:** `CONVERT BREAKS: markdown` 指定でMarkdown有効
- **検証済み:** #062〜#070 インポート・公開で動作確認

### note_import_format_v1 運用フロー

1. draft_rules_v2 に基づきドラフト生成
2. note_import_tests/ に .mt / .txt 生成
3. import_conversion_report で変換確認
4. note の「記事インポート」から .txt アップロード
5. プレビュー確認後に公開

## 8. 現時点の運用結論

### 投稿フロー（現行・手動確認必須）

```
1. source_registry に登録済みか確認
2. draft_rules_v2 に基づき Claude でドラフト生成
3. Codex による BLOCK/WARN チェック
4. BLOCK 修正 → note_import_tests/ に MT/TXT 生成
5. note インポート → プレビュー確認（人間）
6. 公開 → source_registry に note_url・published_date 記録
```

### 運用上の制約と判断基準

**txt/mt は補助ツール**
- インポート形式の安定化には寄与するが、内容品質は Claude + 人間レビューが担保
- 自動生成したMTをそのまま公開することは禁止

**投稿は人間最終確認必須**
- プレビュー画面での視覚確認を省略しない
- note の描画崩れ（特に箇条書き・見出し）は事前確認で防ぐ

**hand review 継続**
- 現状の記事量（〜#090）では hand review が最も確実
- 自動化は補助・チェック用途に限定
- #100 を超えた時点で自動化範囲の再評価を検討

### KPI（次フェーズ目標）

- BLOCK 0件での公開継続
- 公開後修正ゼロ
- source_registry の completeness 100%（公開済み記事）
